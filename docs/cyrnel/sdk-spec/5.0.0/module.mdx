`Module` is the contract every adapter and environment module
extends.

```ts
interface ModuleSetupContext<
  Config extends object = {},
  Secrets extends object = {},
> {
  readonly config: ConfigProvider<Config>;
  readonly secrets: SecretsProvider<Secrets>;
  readonly logger: ModuleLogger;
  readonly credentials?: CredentialProvider;
}

interface Module {
  setup(context: ModuleSetupContext): Promise<void>;
  teardown(): Promise<void>;
}
```

## `setup(context)`

Called once when the module is activated.

- `config`: Scope-bound provider over the module's configuration keys.
  Resolve values on demand with `await config.get("key")` — reads never
  return `undefined`; a declared-but-unset key throws
  `ProviderKeyNotConfigured`.
- `secrets`: Scope-bound provider over the module's secret keys. Values
  are decrypted by the host at read time; resolve with
  `await secrets.get("key")`.
- `credentials`: Present iff the module declares `auth` in its export.
  Resolve per invocation with
  `await credentials.getCredential(schemeName)`.
- `logger`: The host-owned [`ModuleLogger`](/cyrnel/sdk-spec/5.0.0/types#modulelogger).
  Every entry a module emits through it is automatically tagged with
  `type: "module"`, `moduleId`, `moduleType`, and the owning
  `adapterId`/`environmentId`. The module configures its own reduction via
  `logger.redact()` and cannot forge host-managed correlation fields.

For adapter modules, `context` carries the module-level providers backed
by the `modules` database row. Service-level config, secrets, and
credentials are delivered separately through
[`hydrateService`](/cyrnel/sdk-spec/5.0.0/adapter-module#hydrateserviceservice).

For environment modules, `context` is an
[`EnvironmentSetupContext`](/cyrnel/sdk-spec/5.0.0/environment-module#setup) that adds
`bindings`, the host's callback surface.

The host awaits `setup` before declaring the module ready. Throw to abort
activation, the corresponding `modules` row keeps its `enabled` flag, but
the module is not registered as active until the next attempt succeeds.

`setup` may be called more than once over the life of a process if the
module is disabled and re-enabled. Implementations should be idempotent
on internal state.

## `teardown()`

Called when the module is deactivated or the host is shutting down.

Adapters: release pooled resources, flush any in-flight outbound calls,
forget secrets.

Environments: terminate isolates / workers / sub-processes. The host
considers the environment retired once `teardown` resolves; if `teardown`
hangs, the host's shutdown timeout (`SHUTDOWN_TIMEOUT_MS`) will eventually
force-exit.

Errors thrown from `teardown` are caught and logged at `warn` level. They
do not propagate to the caller.

## Lifecycle Notes

- The host **never calls `setup` twice in a row without an intervening
  `teardown`** for the same module instance. Module instances are not
  reused after teardown, the host calls `instantiate()` again if it
  needs the module back.
- For environment modules, `teardown` may be deferred while the module
  drains in-flight executions. See
  [`EnvironmentModule`](/cyrnel/sdk-spec/5.0.0/environment-module#draining).
