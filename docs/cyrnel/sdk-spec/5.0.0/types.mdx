The cyrnel sdk package exports a small set of typescript types that
describe the data cyrnel exchanges between the host, adapters, and
environments. Everything else builds on these.

## `JSONSchema`

```ts
type JSONSchema = Record<string, unknown>;
```

A free-form JSON document. Cyrnel internally validates payloads against the
schema, any valid JSON schema format is fair game. Adapters and environments
treat schemas as opaque.

## `ServiceDefinition`

```ts
interface ServiceDefinition<ServiceDomain = {}, ToolDomain = ServiceDomain>
  extends AuthDefinition {
  readonly name: string;
  readonly summary?: string;
  readonly description: string;
  readonly configSchema: JSONSchema;
  readonly secretsSchema: JSONSchema;
  readonly tools: readonly ToolDefinition<ToolDomain>[];
  readonly adapterDomain: ServiceDomain;
}
```

The shape an adapter returns from `generateService`. Cyrnel persists this
into the `services` table along with an `id`, `hash`, `source`,
`adapter`, and `enabled` flag. See [Services](/cyrnel/docs/v1/services).

- `summary` is an optional short plain-text description shown in lists and
  search. Keep it terse; use `description` for long-form markdown.
- `configSchema` describes per-service configuration (validated on PATCH).
- `secretsSchema` describes per-service secrets (validated on PATCH).
- `schemes` / `security` come from `AuthDefinition` and are required
  (`schemes: {}` / `security: []` mean "none"). See [Authentication](#authentication).
- `adapterDomain` is opaque to cyrnel. Adapters use it to carry
  install-time information that the runtime needs at invoke time.

## `ToolDefinition`

```ts
interface ToolDefinition<Domain = {}> {
  readonly id: string;
  readonly name: string;
  readonly summary?: string;
  readonly description: string;
  readonly inputSchema: JSONSchema;
  readonly outputSchema: JSONSchema;
  readonly adapterDomain: Domain;
  readonly security?: SecurityRequirements;
}
```

The shape of each entry in `ServiceDefinition.tools`. `id` must be a
valid TypeScript identifier; it is what process code addresses. `summary`
is an optional short plain-text label, mirroring the service-level summary.
`security` is a three-way override of the service default: `undefined`
inherits it, `[]` is explicitly anonymous, and a non-empty value fully
replaces it for this tool.

## `ServiceRuntime` and `ToolState`

```ts
interface ToolState<Domain = {}> {
  readonly adapterDomain: Domain;
  readonly security?: SecurityRequirements;
}

interface ServiceRuntime<
  ServiceDomain = {},
  ToolDomain = {},
  Config extends object = {},
  Secrets extends object = {},
> {
  readonly id: string;
  readonly adapterDomain: ServiceDomain;
  readonly tools: Readonly<Record<string, ToolState<ToolDomain>>>;
  readonly config: ConfigProvider<Config>;
  readonly secrets: SecretsProvider<Secrets>;
  readonly schemes: Readonly<Record<string, AuthScheme>>;
  readonly security: SecurityRequirements;
  readonly credentials?: CredentialProvider;
}
```

The live service cyrnel hands to an adapter through
`AdapterModule.hydrateService`. It carries everything the adapter needs to
serve invocations:

- `adapterDomain`: The bag the adapter populated in `generateService`.
- `tools`: Per-tool `adapterDomain` (plus `security`) keyed by tool `id`.
- `config` / `secrets`: Scope-bound providers, not snapshots. Resolve
  values on demand with `await config.get("key")`; secrets are decrypted
  by the host at read time and never stored in runtime state.
- `schemes` / `security`: The declared auth contract (see
  [Authentication](#authentication)).
- `credentials`: Present iff `schemes` is non-empty. Resolve an owned
  credential per invocation with
  `await credentials.getCredential(schemeName)`; credential IDs are
  intentionally not exposed.

Adapters should treat this as the source of truth and refresh their
internal state every time `hydrateService` is called. Do not log secret
or credential values.

## Providers

`setup()` receives capabilities, not snapshots:

```ts
interface ConfigProvider<Config extends object = {}> {
  get<K extends keyof Config>(key: K): Promise<ConfiguredValue<Config[K]>>;
}

interface SecretsProvider<Secrets extends object = {}> {
  get<K extends keyof Secrets>(key: K): Promise<ConfiguredValue<Secrets[K]>>;
}
```

Providers are permanently bound to one owner scope — `get(key)` cannot
target another module or service — and expose single-value reads only.
Calling with an undeclared key throws `ProviderKeyNotDeclared`;
a declared-but-unset key throws `ProviderKeyNotConfigured`. Reads never
return `undefined` for a missing value (`ConfiguredValue<T>` strips only
the absent-value channel; explicit `null` stays `null`).

## Authentication

```ts
type AuthScheme =
  | ApiKeyAuthScheme
  | BasicAuthScheme
  | HttpAuthScheme
  | OAuth2AuthScheme;

interface AuthDefinition {
  readonly schemes: Readonly<Record<string, AuthScheme>>;
  readonly security: SecurityRequirements;
}

type SecurityRequirement = Readonly<Record<string, readonly string[]>>;
type SecurityRequirements = readonly SecurityRequirement[];

type ResolvedCredential =
  | { readonly type: "apiKey"; readonly value: string }
  | { readonly type: "basic"; readonly username: string; readonly password: string }
  | { readonly type: "bearer"; readonly token: string }
  | { readonly type: "oauth2"; readonly accessToken: string; readonly expiresAt: number; readonly scopes?: readonly string[] };

interface OAuthClient {
  readonly id: string;
  readonly provider: string;
  readonly clientId: string;
  readonly tokenUrl: string;
  readonly authorizationUrl?: string | null;
  readonly clientAuthMethod: string;
  readonly redirectUris: readonly string[];
  readonly availableScopes: readonly string[];
}

interface CredentialProvider {
  getCredential(schemeName: string): Promise<ResolvedCredential>;
}
```

- `AuthScheme` covers `apiKey` (`header`/`query`/`cookie`), `basic`,
  `http` (bearer only), and `oauth2`
  (`authorizationCode`/`clientCredentials`/`deviceCode`). There is no PKCE
  challenge-method field — the host always enforces `S256`.
- `SecurityRequirements` is an OR-of-AND-groups mapping scheme names to
  scopes. Scope arrays MUST be empty for non-OAuth2 schemes; adapters pick
  the first satisfiable group in declaration order.
- `AuthDefinition` is shared by `ModuleExport.auth`,
  `ServiceDefinition`, and registry well-known `auth`. A present module
  `auth` must declare at least one scheme; `schemes` non-empty implies
  the `credentials` capability exists (it does not imply credentials
  are already configured).
- `ResolvedCredential` is what the host hands the adapter per
  invocation. `oauth2.scopes` carries the credential's **granted**
  scopes (never the request): adapters enforce required scopes
  against this list, and an absent list means "unknown" — treat it as
  empty (fail closed for non-empty requirements).
- `OAuthClient` is a global, reusable app registration backing any
  number of owner-scoped `oauth2` credentials. `provider` is required
  but is a display/grouping label only — it never participates in
  client resolution and implies no provider-specific OAuth behavior.
  `availableScopes` is required and is the allow-list for requested
  scopes (`[]` = the client may only back unscoped credentials);
  there is no unconstrained state.
- `CredentialProvider` is owner-scoped and host-owned: within one
  owner scope at most one credential exists per scheme name
  (host-enforced `(owner, scheme)` uniqueness), so
  `getCredential(schemeName)` is unambiguous. The host resolves owned
  credentials on demand and refreshes OAuth2 inline; branch selection
  across multi-branch `SecurityRequirements` stays adapter-owned and
  must be deterministic (first satisfiable group in declaration
  order).

## `InvokeInput`

```ts
interface InvokeInput {
  serviceId: string;
  toolId: string;
  parameters: Record<string, unknown>;
}
```

The payload of every tool call:

- Environment modules receive it through `EnvironmentBindings.invokeTool`.
- Adapter modules receive it through `AdapterModule.invoke`.
- The host validates `parameters` against the tool's `inputSchema` before
  the adapter sees it (adapter-side validation is optional but
  recommended).

## `ToolDocsInput`

```ts
interface ToolDocsInput {
  serviceId: string;
  toolId: string;
  description: string;
  inputSchema: JSONSchema;
  outputSchema: JSONSchema;
}
```

Passed to `EnvironmentModule.generateToolDocs` when the API serves
`GET /tools/:serviceId/:toolId/docs`. The environment is expected to
return Markdown.

## Module logging

The host owns all logging. A module receives a single `ModuleLogger` through
its `setup` context and never constructs a root logger. Every entry a module
emits is automatically tagged with `type: "module"`, `moduleId`,
`moduleType`, and the owning `adapterId`/`environmentId`, these correlation
fields are host-managed and the module cannot forge or override them.

### `MODULE_LOG_LEVELS` and `ModuleLogLevel`

```ts
const MODULE_LOG_LEVELS = [
  "trace",
  "debug",
  "info",
  "warn",
  "error",
  "fatal",
] as const;

type ModuleLogLevel = (typeof MODULE_LOG_LEVELS)[number];
```

The severity levels a module logger accepts. The API maps these to its own
internal level vocabulary, so modules are insulated from API-specific level
names.

### `ModuleLogBindings`

```ts
interface ModuleLogBindings {
  phase?: string;
  event?: string;
}
```

The only correlation fields a module may set. `phase` groups a span of work
(e.g. `"setup"`, `"invoke"`, `"execution"`), and `event` is a structured key
describing a specific occurrence (e.g. `"adapter-request"`). All other
correlation fields (`moduleId`, `moduleType`, `adapterId`/`environmentId`,
`serviceId`, `toolId`, `executionId`, `dispatchId`, `requestId`) are set by the
host and ignored if a module attempts to supply them.

### `ModuleLogPayload`

```ts
type ModuleLogPayload = Record<string, unknown>;
```

The free-form structured object a module passes alongside an optional message.
Values are subject to the module's own `redact()` patterns and the host
baseline before being stored.

### `ModuleLogger`

```ts
interface ModuleLogger<C = ModuleLogBindings> {
  readonly context: Readonly<C>;
  trace(payload?: ModuleLogPayload, message?: string): void;
  debug(payload?: ModuleLogPayload, message?: string): void;
  info(payload?: ModuleLogPayload, message?: string): void;
  warn(payload?: ModuleLogPayload, message?: string): void;
  error(payload?: ModuleLogPayload, message?: string): void;
  fatal(payload?: ModuleLogPayload, message?: string): void;
  isLevelEnabled(level: ModuleLogLevel): boolean;
  child<Next extends ModuleLogBindings>(bindings: Next): ModuleLogger<C & Next>;
  redact(patterns: readonly string[]): ModuleLogger<C>;
}
```

Usage:

```ts
const patterns = await context.config.get("redactionPatterns").catch(() => []);
// configure reduction for yourself from your own config field
this.logger = context.logger.redact(patterns).child({ phase: "setup" });

this.logger?.info({ event: "request", path }, "Sending request");
const scoped = this.logger?.child({ phase: "invoke", event: "adapter-request" });
scoped?.warn({ event: "rate-limited" }, "Upstream throttled");
```

- `child(bindings)` returns a new logger that merges only `phase`/`event`.
  Host-owned correlation fields are carried over and cannot be overwritten.
- `redact(patterns)` returns a **new** logger that applies the module's path
  patterns **additively** on top of a non-disableable host baseline
  (secrets / tokens / passwords / authorization). Chained `redact()` calls
  accumulate patterns; non-string or empty-split patterns are ignored so a
  malformed pattern can never redact the whole payload. The host never pushes
  patterns into the setup context - reduction is configured by the module, for
  the module.
- `context` is `Readonly`: a module reads but never mutates the logger's
  bound metadata.

### `ModuleSetupContext`

```ts
interface ModuleSetupContext<
  Config extends object = {},
  Secrets extends object = {},
> {
  readonly config: ConfigProvider<Config>;
  readonly secrets: SecretsProvider<Secrets>;
  readonly logger: ModuleLogger;
  readonly credentials?: CredentialProvider;
}
```

Passed to `Module.setup`. `config` and `secrets` are scope-bound
providers over the validated module-level keys from its
`configSchema`/`secretsSchema` (see [Providers](#providers)); `logger` is
the host-owned logger described above; `credentials` is present iff the
module declares `auth` in its export. The adapter-vs-environment
distinction lives in the `AdapterModule`/`EnvironmentModule` interfaces,
not in the context type — environment modules additionally receive
`bindings` (see
[`EnvironmentSetupContext`](/cyrnel/sdk-spec/5.0.0/environment-module#setup)).

## Execution constants

```ts
const EXECUTION_STATES = ["queued", "running"] as const;
type ExecutionState = (typeof EXECUTION_STATES)[number];

const EXECUTION_EXIT_STATES = [
  "failed",
  "success",
  "timeout",
  "canceled",
] as const;
type ExecutionExitState = (typeof EXECUTION_EXIT_STATES)[number];
```

The vocabulary an environment uses to report progress. `ProcessService`
adds `suspended`, `idle`, `terminating`, and `terminated` on top — host-only
states for approval gating (`suspended` with `pendingApprovalIds`, `terminated`
from orphan recovery), not environment-reported. See [Execution](/cyrnel/sdk-spec/5.0.0/environment-execution) and
[Processes](/cyrnel/docs/v1/processes).

Tool invocations that hit `ask` policy are parked by the host until
`approved`/`denied`/`expired` (via `approval_requests` CAS); denied/expired surface
as `JSON.stringify({ __ivmError: "Approval denied|expired" })` catchable in the sandbox.
