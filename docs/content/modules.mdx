MCI coordinates two kinds of modules:

- **[Adapter modules](/content/modules/adapters)** translate environment
  invocations into calls to end services.
- **[Environment modules](/content/modules/environments)** execute the code
  clients submit.

Both implement the base `Module` interface from `@mci/sdk` (`setup`,
`teardown`); each adds its own contract on top.

## The Module Registry

Modules are registered with the `ModuleService` at startup. There are two
sources:

1. **Built-in modules**, shipped as workspace packages. The current set:
   - `openapi` — adapter, in `packages/modules/openapi`
   - `typescript-ivm` — environment, in `packages/modules/typescript-ivm`
2. **Custom modules**, loaded from `$MCI_DATA_DIR/modules/<name>/`. Each
   directory must contain a `module.json`:

   ```json
   {
     "name": "my-adapter",
     "type": "adapter",
     "description": "Talks to my service",
     "main": "./index.js"
   }
   ```

   `main` is an ES module exporting `instantiate(): AdapterModule` or
   `EnvironmentModule`. See
   [Writing a custom module](/spec/writing-a-custom-module).

The registry is reflected to the `modules` table. Three things can happen
during reconciliation:

- **Insert** — a registered module that isn't in the DB yet. Default
  `enabled: true`, `orphaned: false`.
- **Orphan** — a row in the DB whose module is no longer registered (e.g.
  the custom folder was removed). Set `orphaned: true, enabled: false`. The
  row stays so its config/enablement is preserved if the module reappears.
- **Restore** — an orphaned row whose module is registered again. Clear
  `orphaned: false`.

`POST /modules/reload` re-scans `$MCI_DATA_DIR/modules/` and reruns
reconciliation. Use it after dropping a new custom module into the directory.

## Activation

Activation = "this module is now ready to take work". It is per-module-type:

- **Adapters** activate eagerly. On startup MCI activates every adapter row
  with `enabled = true, orphaned = false`, runs `setup({})`, then hydrates
  every enabled service that targets it.
- **Environments** activate one-at-a-time. Only the environment whose row is
  enabled gets activated. Enabling a different environment disables the
  previously-enabled one in the DB and swaps the active reference.

### Draining environments

When the active environment is replaced or disabled, it doesn't disappear —
it becomes **draining**. New executions go to the newly-active environment
(or fail with `503` if none). The draining environment keeps running its
in-flight executions; once all of them finish, MCI tears it down. This means
a `POST /modules/:envId/enabled` with `enabled: false` returns immediately,
but the actual teardown may happen seconds later.

## Module API

| Method | Path | Notes |
| --- | --- | --- |
| `GET` | `/modules` | Filterable by `query`, `type`, `isBuiltin`, `enabled` |
| `GET` | `/modules/:moduleId` | Single module |
| `POST` | `/modules/:moduleId/enabled` | Toggle `{ enabled: boolean }` |
| `POST` | `/modules/reload` | Re-scan custom modules from disk |

Enabling an orphaned module returns `409`.

A module record:

```ts
interface ModuleManifestRecord {
  id: string;
  name: string;
  description: string;
  type: "adapter" | "environment";
  isBuiltin: boolean;
  enabled: boolean;
  orphaned: boolean;
}
```

## Picking the Right Module Type

- If you need to **let user code reach a new kind of end service**, write an
  **adapter**.
- If you need to **change how code is executed** (different language,
  different sandbox, different permission model), write an **environment**.

Most extension work in the wild is adapter work. Environment modules are a
heavier commitment because they own the security boundary user code runs
inside.
