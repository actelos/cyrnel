This page maps the security model of an MCI deployment: who is trusted to
do what, where the boundaries are, and where the current implementation
falls short of an ideal one. Read it before exposing MCI beyond a single
local machine.

## Trust Model in One Diagram

```
        ┌──────────────────────────────────────────────────────────┐
        │                       MCI host process                    │
        │                                                          │
        │   ┌─────────────────┐    ┌────────────────────────────┐  │
        │   │  HTTP API       │    │  Module registry           │  │
        │   │  (auth gate)    │    │  • Adapter modules         │  │
        │   │                 │    │    (full host privileges)  │  │
        │   │                 │    │  • Environment module      │  │
        │   │                 │    │    (sandboxes user code)   │  │
        │   └────────┬────────┘    └──────────┬─────────────────┘  │
        │            │                        │                    │
        │   ┌────────▼────────────────────────▼────────────────┐   │
        │   │           SQLite (libSQL): mci.db                │   │
        │   │   services / tools / configs / encrypted secrets │   │
        │   └──────────────────────────────────────────────────┘   │
        └──────────────────────────────────────────────────────────┘
                ▲                                       │
                │ Authorization: Bearer <MCI_API_KEY>   │ outbound calls
                │                                       ▼
       ┌────────────────┐                       ┌────────────────┐
       │  API clients   │                       │  End services  │
       └────────────────┘                       └────────────────┘
```

There are three actors that matter:

- **The operator.** Whoever runs the MCI process. They choose the env vars,
  the modules on disk, the key material, and what to expose.
- **The API caller.** Anyone with a valid `MCI_API_KEY` (or any caller if
  the API runs anonymously). They can install services, write secrets,
  toggle modules, and run code.
- **The end services.** Whatever the adapters reach. They are downstream
  of MCI and largely outside its control.

Everything else (user code in the sandbox, adapters loaded from disk, the
web UI) is a tool the operator chooses to trust.

## API Surface

- **Authentication is one static bearer token** (`MCI_API_KEY`). No scopes,
  no expiry. Anonymous mode is intended for `127.0.0.1` only.
  See the [README](https://github.com/actelos/mci#authentication).
- **No rate limiting** is enforced by the API. A noisy or hostile caller
  will be felt directly by adapters and end services.
- **Error envelopes** are intentionally terse (`{ "error": "..." }`). They
  do not leak stack traces, but `5xx` messages occasionally include
  exception text. Don't proxy them to untrusted users verbatim.

## Modules

### Adapter modules

Adapter modules are the most security-sensitive component MCI loads, for
three reasons:

1. **They run with full host privileges.** Custom adapters loaded from
   `$MCI_DATA_DIR/modules/<name>/` execute in the API's Node.js process.
   They can read environment variables, open files, make arbitrary
   network requests, and call native code. There is no sandbox between
   an adapter and the host.
2. **They receive decrypted secrets.** `ServiceState.secrets` is the
   plaintext secret document the operator stored for a given service.
   Every enabled adapter sees every secret of every service it owns.
3. **They can choose what to persist.** Adapters are expected to keep
   per-service state in memory — but a malicious or careless adapter can
   write that state anywhere it pleases.

#### Operator guidance

- Treat `$MCI_DATA_DIR/modules/` as part of the codebase. Review additions
  with the same scrutiny you give to a `node_modules` dependency.
- Disable adapters you aren't actively using. A disabled adapter still has
  its row in `modules`, but its `setup()` is never called.
- Don't share `MCI_SECRETS_KEY` across deployments. A leaked key plus a
  stolen `mci.db` is equivalent to leaking every credential the deployment
  has stored.
- If you're integrating a third-party adapter, verify what it does with
  secrets — at minimum, that it does not log them, persist them to disk,
  or forward them anywhere outside the target service.

See [Adapter Modules](/content/modules/adapters) for the interface and
expectations.

### Environment modules

The active environment owns the sandbox user code runs inside. The
bundled `typescript-ivm`:

- Runs each execution in an `isolated-vm` isolate with a 128 MB memory
  cap (default).
- Provides **no module loader, no filesystem, no network, and no Node
  built-ins**. The only outbound channel is the small set of `__mci_*`
  references MCI installs.
- Terminates the isolate on timeout and recreates the worker slot.

A few caveats:

- **CPU is shared with the host process.** A tight loop occupies an
  isolate's worker slot until the timeout fires; with the default pool
  size of 2, two such loops block all process execution.
- **Tool invocations bypass the sandbox.** When user code calls
  `mci.services[id].tools[t].invoke(...)`, the request leaves the
  isolate and runs in the host through the adapter. The sandbox limits
  what code can *do directly*, not what tools it can *ask MCI to call*.
- **Per-tool authorization is the gating mechanism.** A tool you don't
  want a process to call should be disabled (`POST
  /tools/:serviceId/:toolId/enabled`).

See [Environment Modules](/content/modules/environments).

## Secrets

Secrets live in `service_secrets.payload` as AES-256-GCM ciphertext with a
fresh 12-byte IV per write. The auth tag is stored alongside.

- **The key** is `MCI_SECRETS_KEY`, base64-encoded, decoded to 32 bytes.
  Anything else (missing, short, long, non-base64) fails the request with
  `500 Secrets key is not configured`.
- **The example key in `.example.env`
  (`AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=`) decodes to 32 NUL
  bytes.** It is not a secret. Anything encrypted with it is effectively
  in plaintext as soon as the database leaves the machine. **Replace it
  before storing anything.**
- **There is no key rotation.** Rotating means: re-`PATCH` every service's
  secrets through the API (which decrypts with the old key, re-encrypts
  with the new). Plan for a re-run during cutover.
- **Secrets never leave the API in plaintext.** There is no
  `GET /services/.../secrets` endpoint. Patches operate against the
  decrypted document in memory.

## Service Installation (Definition Fetching)

`POST /services/install` fetches the URL the caller supplies, hashes it,
and passes it to the adapter's `generateDefinition`. The fetcher has a few
guards:

- Hard timeout of 10 seconds per request.
- Maximum response body of 2 MiB.
- IP-literal hostnames whose range is not `unicast` are rejected
  (loopback, link-local, multicast, private-v4 ranges).

But:

- **DNS names are not resolved or pinned.** A caller can hand MCI any
  hostname; the SSRF guard only triggers when the hostname is *already*
  an IP literal. `http://internal.example.com/...` is fetched without
  comment, even if it resolves to `10.0.0.5`. Likewise, `http://localhost/`
  bypasses the guard because `localhost` is not a literal IP.
- **There is no allowlist.** Anyone with API access can ask the server to
  hit any URL.

#### Operator guidance

- Treat the API key as the security boundary. Do not expose
  `/services/install` (or the API at all) to clients you wouldn't trust
  to make outbound network requests from the host.
- If you need a stricter posture, run MCI inside a network namespace or
  egress firewall that restricts which hosts it can reach.

## Web UI

`apps/web` is a **client-side** dashboard. Two consequences:

- **`VITE_AUTH_USERNAME` and `VITE_AUTH_PASSWORD` are not auth.** The
  login form compares typed values against env vars baked into the
  bundle. Anyone with the bundle can read them.
- **`VITE_MCI_API_KEY` is exposed to anyone who can load the page.** When
  the web UI is hosted publicly, this is equivalent to publishing the
  API key.

The intended deployment story is "the web UI is a local-dev convenience";
expose the API with proper auth, and treat the dashboard as a development
tool rather than a production console.

## Data at Rest

| What | Where | Protection |
| --- | --- | --- |
| Service metadata, tools, schemas | `services`, `tools` tables | None (plaintext). |
| Service configuration (JSON-Patch-edited) | `service_configurations.payload` | None (plaintext). |
| Service secrets | `service_secrets.payload` | AES-256-GCM with `MCI_SECRETS_KEY`. |
| Module enable/orphan state | `modules` | None (plaintext, but boolean flags only). |
| Process records, stdout, stderr, output | In-memory only | Lost on restart. |

If `mci.db` leaks, the encrypted secrets are protected by the key only.
Configuration is not — operators must avoid storing credentials in
`config` blocks. The `secretsSchema` exists for that exact reason; use it.

## Defaults Worth Hardening

- Replace `MCI_SECRETS_KEY` before first use.
- Set `MCI_API_KEY` whenever the API listens on anything other than
  `127.0.0.1`.
- Restrict the host's outbound network if `/services/install` is
  reachable by untrusted callers.
- Don't deploy the web UI publicly with credentials baked into the
  bundle.
- Review adapters before dropping them into `$MCI_DATA_DIR/modules/`.
